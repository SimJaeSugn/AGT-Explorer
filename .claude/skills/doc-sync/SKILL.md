# doc-sync — 기획·개발 문서 ↔ 코드 상태 동기화

개발이 진행되면 문서는 금세 낡는다. 문서가 "완료"라는데 코드가 없거나, 다 만들었는데
문서엔 미착수로 남아 있으면, 문서는 거짓말이 되고 신뢰를 잃는다. 이 스킬은 **각 구현 단계가
끝날 때마다 문서의 상태 표기를 코드 사실에 맞춰** 문서를 살아있는 진실로 유지한다.

> **이 스킬이 바꾸는 것:** 상태 표기(✅/🟡/🔜)·기준일·구현 파일 매핑·체크박스.
> **바꾸지 않는 것:** 요구사항 문구·수용기준·MoSCoW 분류(스코프) 자체. 스코프 변경은 PM/사용자 몫이다.

## 언제 실행하나 (게이트)
- **team-dev/dev-orchestrator의 각 구현 Phase 완료 직후** (예: P2 통과 → 동기화 → P3 진입). 동기화 없이 다음 Phase로 넘어가지 않는다.
- 전체 통합 검증(team-dev Phase 5) 시 한 번 더.
- 사용자가 "문서 동기화/상태 갱신"을 직접 요청할 때(전체 감사 모드).

## 실행 방식
이 작업은 `doc-synchronizer` 에이전트가 수행한다. PM/오케스트레이터는
`Agent(subagent_type: "doc-synchronizer", model: "opus")`로 호출하고, 방금 완료된 Phase와
그 검증 결과 요약, 프로젝트 루트를 전달한다. 에이전트는 아래 절차를 따른다.

## 절차

### 1. 입력 파악
- 무엇을 동기화하나: 특정 Phase 완료분인가, 전체 감사인가.
- 직전 동기화 기준일을 문서 헤더에서 확인(그 이후 변경분 위주로 갱신).

### 2. 구현 사실 수집 (코드가 진실 출처 — 추측 금지)
실제 상태를 코드·검증으로 확인한다:
- `Grep`/`Glob`로 기능별 구현 존재 확인(슬라이스·핸들러·컴포넌트·IPC 채널).
- 검증 근거: `package.json`의 `verify:*` 스크립트, 타입체크/린트/빌드 통과 여부, 테스트 결과.
- 진입점만 있고 동작은 없는 경우 식별(예: 채널 타입만 동결·`// impl: Pn` 주석·단축키만 등록·`isGrid=false` 류 플래그).

### 3. 상태 판정
| 표기 | 조건 |
|------|------|
| ✅ 완료 | 코드 존재 + 관련 검증 통과(동작/타입/빌드/verify) |
| 🟡 부분 | 코드 일부만 / 실측·검증만 남음(예: 성능 1.5초 실측은 릴리스 단계) |
| 🔜 미착수 | 미구현. 계약·키·타입만 예약된 경우도 🔜 — 괄호로 "○○만 예약" 명시 |

보수적으로: 애매하면 ✅ 대신 🟡. 진입점만이면 🔜.

### 4. 문서별 갱신 (상태 표기만)
- **`docs/roadmap.md`** — 상태의 **단일 출처**. `§0.5 진행 현황`(Phase별 상태표·예약 진입점 표·검증 누계), `§1 요약표`의 상태 컬럼, 각 `### Pn` 단계 제목 배지를 갱신.
- **`docs/PRD.md`** — `§6 MoSCoW` 체크박스(`[ ]`↔`[x]`)와 섹션 상태 표기, `§12 마일스톤` 상태 컬럼, 헤더 기준일/상태.
- **`docs/user-stories.md`** — `백로그 요약표`의 상태 컬럼, 미착수/부분 스토리 제목 배지, 헤더 상태 한 줄.
- **`docs/features.md`** — 헤더 구현 상태 배너(어떤 우선순위가 완료/미착수인지, 예약 진입점 목록).
- **`docs/flows.md`** — 헤더 상태 한 줄(핵심 플로우 구현 여부).
- **`docs/architecture/traceability.md`** — 기능→구현 파일 매핑이 **실제 경로와 일치**하는지 점검(유령 매핑=설계만 있고 코드 없음 / 누락=코드 있는데 매핑 없음). 불일치는 정정하고 보고.

### 5. 일관성 정합
- 모든 문서가 **동일 기준일**(오늘 날짜는 호출자가 전달하거나 `currentDate` 컨텍스트를 사용 — 스크립트에서 `Date.now()`로 추정하지 말 것)과 **동일 범례(✅/🟡/🔜)**를 쓰게 한다.
- 한 기능의 상태가 문서마다 다르면 `roadmap §0.5`를 기준으로 통일한다.

### 6. 드리프트 처리 (탐지 시 반드시 보고)
| 드리프트 | 조치 |
|----------|------|
| 문서=✅ but 코드 없음 | 문서를 코드 기준으로 정정(🔜/🟡) + **경고 보고** |
| Must인데 미구현 | 🔜로 표기 + 경고(릴리스 차단 후보로 보고) |
| 구현됐는데 기획에 없음(스코프 일탈) | 문서에 임의 추가 금지 → **드리프트로만 보고**해 PM/사용자 결정에 올림 |
| traceability 매핑이 실제 파일과 불일치 | 매핑 정정 + 보고 |

### 7. 검증 후 보고
- 갱신 후 문서 간 상태 모순 0, 기준일 일치 확인.
- **동기화 보고** 반환: (a) 갱신한 문서·항목, (b) 드리프트 분류·위치·권고, (c) 남은 모순/의사결정 필요 항목.

## 주의 (왜 이렇게 하나)
- **문서는 의사결정의 근거다.** 상태가 틀리면 "다 됐는데 왜 또?"나 "안 됐는데 왜 됐다고?" 같은 혼선이 생긴다. 그래서 코드 사실로만 판정한다.
- **스코프는 사람이 정한다.** 구현이 앞서갔다고 문서가 따라가 스코프를 늘리면, 기획의 권위가 무너진다. 그래서 일탈은 추가가 아니라 보고다.
- **부분은 부분으로.** 성능 미실측·일부 미구현을 ✅로 적으면 릴리스 판단이 왜곡된다. 그래서 🟡를 남긴다.

## 테스트 시나리오
- **정상 흐름:** team-dev에서 P4(파일작업) 통과 → PM이 doc-synchronizer 호출(완료 Phase=P4 + 검증요약) → 에이전트가 roadmap P4 배지/요약표·PRD Must 체크박스·user-stories 관련 스토리 상태를 ✅로, traceability 매핑을 실제 파일로 갱신 → 모순 0 확인 후 보고 → PM이 P5 진입.
- **드리프트 흐름:** 동기화 중 "휴지통 비우기 화면"이 코드엔 없는데 features에 완료처럼 보임 → 문서를 🔜로 정정하고, 반대로 로드맵 외 추가된 `build-installer.ps1`은 기획에 없으므로 스코프 일탈로 플래그만 → 보고서에서 PM에게 결정 요청.
