# ADR-003 — IPC 계약 스타일

상태: 제안 · 2026-06-06

## 맥락
Renderer는 FS/OS에 직접 접근하지 못하고 **Preload→Main IPC로만** 작업한다(ADR-005). 다뤄야 할 통신은 (a) 단발 요청-응답(디렉토리 목록·stat·경로검증), (b) **장시간 작업의 진행률 스트림·충돌 질의·취소**(복사/이동/삭제, US-5.2), (c) **대형 디렉토리 증분 스트리밍**(US-5.6), (d) 권한/네트워크 오류의 명시적 전파(features F장). 계약이 깨지면 런타임 크래시 → **컴파일 타임에 잡고 싶다**.

## 선택지 비교

| 스타일 | 장점 | 단점 |
|---|---|---|
| **타입공유 RPC(invoke/handle) + 이벤트 스트림(채택)** | 단발=invoke로 간결, 장시간=이벤트로 진행/취소, shared 타입으로 컴파일 검증, 보안검증 지점 명확 | 채널/타입을 직접 관리(경량 래퍼 필요) |
| 단일 거대 `invoke('rpc', {method, args})` 디스패처 | 채널 1개로 단순 | 타입 안전 약화, 진행률 스트림 표현 부자연, 보안 화이트리스트 흐려짐 |
| 자동 RPC 프록시(예: tRPC형/메서드 자동 노출) | DX 좋음 | "전체 노출" 유혹→보안 footgun, 스트림/취소 모델 부자연, Electron 보안 권고와 상충 |
| 코드젠 스키마(protobuf 등) | 강한 계약 | 로컬 단일 앱엔 과설계, 빌드 복잡 |

## 결정
**`shared/ipc`에 채널 상수 + 요청/응답·이벤트 TS 타입을 단일 출처로 두고**, 단발은 `invoke/handle`, 장시간 작업·디렉토리 스트림은 `operationId/streamId` 기반 단방향 이벤트로 처리한다. 응답은 `Result<T, FileOpError>` 판별 유니온으로 도메인 오류를 1급 전파한다. (system-architecture 3장)

## 근거
- 진행률 200ms 갱신·취소·충돌 질의는 요청-응답만으로 부자연 → 이벤트 스트림이 자연스럽다.
- 메서드 단위 채널 노출이 Electron 보안 권고("ipcRenderer 통째 노출 금지")와 정합. Preload가 채널마다 래퍼 1개만 공개.
- shared 타입 공유로 Preload/Main/Renderer 계약 위반을 컴파일 타임 검출.
- 권한 오류를 throw가 아닌 Result로 전파 → UI가 "접근 거부" 사유를 1급으로 표시(flows 3장).

## 트레이드오프
- 채널/타입을 수동 관리(자동 프록시 대비 약간의 보일러플레이트) → 가벼운 헬퍼로 흡수.
- 스트림 구독 해제/누수 관리 책임이 생김 → streamId 라이프사이클 규약으로 관리.
