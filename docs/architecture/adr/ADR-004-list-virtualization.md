# ADR-004 — 파일목록 가상화 방식

상태: 제안 · 2026-06-06

## 맥락
**10,000개 항목 폴더 첫 화면 1.5초**, 입력 200ms 반영, 작업 중 UI 비차단(US-5.6, US-4.1, PRD 3·7장). 1만~수십만 행을 모두 DOM에 그리면 렌더·메모리·스크롤이 무너진다(R1). 보기는 details/list(행 기반)와 grid/썸네일(S, 셀 기반)이 있고, 패널이 동시에 2~4개 떠 각자 스크롤한다.

## 선택지 비교

| 옵션 | 장점 | 단점 |
|---|---|---|
| **윈도잉(가시영역만 렌더) + 스트리밍 증분(채택)** | DOM 노드 수십 개로 일정, 1만+에서도 매끈, 첫 청크 즉시 렌더로 1.5초 충족 | 가변 높이/그리드 측정 로직 필요 |
| 전체 렌더 + CSS `content-visibility` | 구현 단순 | 1만+에서 레이아웃/메모리 부담, 200ms 위협 |
| 페이지네이션 | 단순 | 탐색기 UX와 이질적(연속 스크롤 기대), 채택 부적합 |
| 라이브러리 직접(react-window/virtuoso류) vs 자체 구현 | 검증된 윈도잉 빠르게 확보 | 그리드·다중선택·D&D·인라인편집 통합 제약 |

## 결정
- **윈도잉(가상 스크롤)**: 가시 영역 + 오버스캔만 렌더.
  - **details/list**: 고정 행 높이 → 단순·고성능 고정 크기 윈도잉.
  - **grid(S)**: 열 수×셀 높이 기반 그리드 윈도잉.
- **스트리밍 증분 적재**: `fs:list:start→chunk→done`로 받은 엔트리를 점증 추가, 첫 청크 도착 즉시 스피너 해제·첫 화면 표시(system-architecture 3·software-architecture 6장).
- 구현은 **검증된 윈도잉 코어를 우선 검토**하되, 다중선택/D&D/인라인 이름편집/가변 보기 통합 제약이 크면 얇은 자체 윈도잉으로 대체(M1 스파이크에서 확정).

## 근거
- "첫 화면 1.5초"의 병목은 전체 스캔이 아니라 **첫 표시 시점**이다 → 스트리밍 첫 청크 즉시 렌더가 직접 해법.
- 윈도잉으로 DOM 수를 항목 수와 무관하게 일정화 → 다중 패널 동시에도 비차단.
- 정렬/필터는 도메인 순수 함수+메모이즈로 분리, 윈도우는 파생 결과만 그린다.

## 트레이드오프
- 윈도잉으로 화면 밖 항목은 DOM에 없어 브라우저 기본 `Ctrl+F`·접근성 트리에 한계 → 자체 검색(Ctrl+F)·ARIA 행 레이블로 보완(PRD 접근성).
- 가변 높이/그리드 측정 코드 복잡도 증가.
- 라이브러리 채택 시 다중선택·D&D 통합을 위해 커스터마이즈 비용 발생 가능.
